## Discussion — ARC card data and PCI

- **[[Tonya Fernelius|Tonya]]: the ARC files are not masked.** Both the **legacy format**
  and the **new JSON file** contain **unmasked card numbers**, including the new
  **multiple-form-of-payment** transactions. There is **no setting in ARC** to choose
  masked vs. unmasked — "either we get the file unmasked or we don't get a file at all."
- Matt confirmed the context: the **PCI meetings** have been running the last two days, so
  we need to be sure what we **store** fits the PCI requirements. Either **mask** or
  **truncate** the visible data — **truncation is definitely allowed**.
- Open question that gates the design: **do we actually need unmasked card data** to match
  transactions for reconciliation?
  - **Reconciliation today doesn't need it** — Tonya does those off **ticket numbers**,
    not card numbers.
  - **Expense probably does**, because it matches in the opposite direction and there
    isn't always a ticket number on our side (travellers can book direct with a carrier).
- History worth reusing: when card data was first masked to **first four + last four**, it
  produced **false matches** across clients. They had **Agresso** re-mask to **first six +
  last four**, which behaved correctly. Worth knowing if expense ends up matching on card.
- On **encrypting the stored files**: Matt's point is that encryption alone isn't the
  question — PCI cares about **where the keys come from, where they're stored, and who has
  access**. That has to be worked out with **[[Mike Harris]]** and his team.
- Useful lever from Tonya: in **ARC** everything is **masked in the UI per user**, but the
  **file download isn't** — so we can **limit who can download the file**. She noted
  [[Mike Harris|Mike]] and [[James Proctor|James]] already want to talk about ARC users
  and access.
- Tonya has a **file containing our first multiple-form-of-payment transactions** — a good
  example to look at, since we'll see it often. She emailed it Monday **2026-08-10** and
  will forward it again.
